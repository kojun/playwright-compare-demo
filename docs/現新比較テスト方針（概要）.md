# 現新比較テスト方針（概要・リライト対応版）

## 1. はじめに ― 現新比較テストの位置づけ

本プロジェクトは、既存システム（現行）をリライトして新アーキテクチャへ移行する、いわゆる**モダナイゼーションプロジェクト**である。  
ここで実施する「現新比較テスト」は、単なる移行検証ではなく、**将来的な品質保証体制を見据えたテスト資産化の第一歩**として位置づける。

### 現新比較テストの適用範囲
| 区分 | 対象 | 備考 |
|------|------|------|
| 画面の単機能テスト | Playwrightを用いたE2EレベルのUIテスト | 今回の主対象 |
| 連結テスト（バッチ含む） | API／DB／バッチ間連携 | あとで検討 |

現段階では、まず**画面の単機能テスト**を中心に方針を定義する。  
データは以下のように扱う：

| テスト種別 | 使用データ | 備考 |
|-------------|-------------|------|
| 単機能テスト | 開発用データ | 各画面単位の機能検証を目的 |
| 連結テスト | 本番データをマスクしたもの |  |

## 2. テスト設計の目標

### （１）テストDSLの設計
- 各画面の**仕様書・設計書・実際の画面構成**をもとに、  
  テストシナリオを**DSL（ドメイン固有言語）**として定義する。  
- DSLには「操作手順」「入力値」「期待結果」を含め、  
  Playwrightのテストコードを自動生成可能とする。
- これにより、**非エンジニアでもテスト仕様を定義可能**とする。

### （２）現新比較の自動化
- 生成されたテストコードは**現行環境・新環境の両方**で実行する。  
- 実行結果（画面キャプチャ・DB状態・APIレスポンスなど）を比較し、  
  一致・不一致をレポート化する。  
- 差分はUI仕様差・データ変換差・仕様外動作を明確に切り分ける。

### （３）テスト資産の継続利用（おまけ目標）
- 現新比較テストで得られたDSL・コード・比較ロジックを、  
  新システムの**回帰テスト（リグレッション）資産**として活用できるよう設計する。
- このため、新側HTMLには可能な範囲で**ARIA属性などの意味情報**を埋め込み、  
  将来のUI変更にも強いテスト構造を目指す。

## 4. セレクタ設計方針

### 4-1. セレクタ辞書
画面ごとに要素識別子を定義した**セレクタ辞書**を設ける。  
各要素には優先度つきの複数候補を登録し、Playwrightが順に探索する。

優先順位例：  
`role → aria-label → data-testid → label → text → CSS`

これにより、HTML構造が一部異なっても、テストコードの修正を最小化できる。

### 4-2. フォールバックセレクタ
現側ではARIAなどの構造化ラベルが存在しない可能性が高いため、  
フォールバック方式で柔軟に探索を行う。

例：
```json
{
  "user.id": [
    { "role": "textbox", "name": "ユーザーID" },
    { "label": "ユーザーID" },
    { "css": "input#userId" }
  ]
}
```

### 4-3. 互換レイヤー（必要に応じて）
現行HTMLが極端に古く、セレクタが安定しない場合は、  
Playwright実行時に一時的にARIA属性や`data-testid`を付与する「互換レイヤー」を適用する。  
これはHTMLを直接改変せず、**DOM上でのみ一時的に補完**する方式とする。

## 5. 同一テストコード運用（SSCM：Strict Same Code Mode）

- 現新で完全に同一のテストコードを利用する。  
- 差分はHTML構造・辞書定義・互換レイヤーのみに閉じ込める。  
- テストソースのハッシュ値を記録し、同一コード実行の証跡を残す。

## 6. 本方針の狙いと効果

| 項目 | 効果 |
|------|------|
| **共通DSL** | テスト仕様を標準化し、自動生成を容易にする |
| **SSCM** | 現新での整合性を厳密に保証 |
| **セレクタ辞書** | テスト修正範囲を局所化 |
| **互換レイヤー** | 古いHTMLへの非破壊的適応 |
| **ARIA導入（新側）** | 将来のUI改修にも強い資産化を実現 |

---

## 7. 結論

本方針では、現新比較テストを「移行確認」ではなく、  
**モダナイゼーション後も継続利用できるテスト基盤の構築プロセス**として位置づける。

- 現段階では単機能画面テストを対象とし、DSL化・共通コード化を推進する。  
- 現新差分はテストコードではなく、セレクタ層・補助レイヤーで吸収する。  
- 将来的には連結テストや回帰テストへ発展可能な基盤とする。
